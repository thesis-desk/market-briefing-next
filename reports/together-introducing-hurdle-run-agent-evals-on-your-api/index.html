Together AI : 코딩 에이전트가 우리 API를 잘 쓰는지 반복 실험으로 재야 하고, Hurdle이 그 실험을 자동화한다

해석 Together AI가 사내에서 6개월 동안 만든 에이전트 평가 도구 Hurdle을 오픈소스로 공개했다. 도구는 무료지만, 실제 API를 건드리는 평가를 안전하게 돌리려면 Together Sandbox를 거치도록 설계돼 있다. 그래서 '에이전트 경험' 평가를 자사 샌드박스 수요로 잇는 진입로로 읽힌다. 다만 글은 사용법 안내에 머물고, 자사 평가 결과 수치는 본문에 없다. 상장 종목 판정에 쓸 근거는 약하다.

주장 한 줄

사실

개발자는 이제 코딩 에이전트를 거쳐 API·SDK·문서에 접근하는 경우가 많다. 그러니 플랫폼 회사는 여러 모델·하니스·조건에서 에이전트가 실제 과제를 얼마나 해내는지 반복해서 재야 한다. Together는 그 작업을 자동화하는 npm 라이브러리 Hurdle을 6개월 동안 만들어 오픈소스로 공개했다.

출처 1 · 도입부

해석

제품 출시 글이다. 다만 핵심 메시지는 도구 기능보다 '에이전트가 우리 제품을 잘 쓰는가'(agent experience)를 개발자 플랫폼의 측정 대상으로 정의하는 데 있다고 본다. 이 정의가 퍼지면 문서·SDK·MCP·skill 정비가 반복 측정이 필요한 품질 지표로 바뀐다.

모델·조건·반복 횟수의 조합이 너무 많아 손으로는 평가할 수 없다

원문

Together AI · 블로그 글

이 모든 것을 손으로 조율하는 일은 지독하게 지루하다. 지난봄 Together에서 평가를 시작하면서 우리가 몸으로 겪어 알게 된 사실이다.

출처 1 · 도입부

사실
  • 과제(task)는 개발자가 에이전트에게 건넬 법한 프롬프트 한 개다. Hurdle은 에이전트에 과제를 실행시키고, 세션을 기록하고, 채점한다.
  • 대상 에이전트는 Claude Code와 Codex 두 가지다.
  • 조건(condition)은 에이전트가 처음 갖고 시작하는 맥락이다. 같은 과제를 MCP 서버를 설치한 에이전트와 설치하지 않은 에이전트에 돌려 그 효과를 비교하는 식으로 쓴다.
  • 지정한 에이전트·모델 조합마다 모든 과제를 돌린다. 에이전트는 같은 과제도 매번 다르게 실행하므로, 과제·모델·조건 조합을 여러 번 반복해 통과율을 낸다.

출처 1 · How Hurdle works

사실
  • 사례 과제: 사용 가능한 GPU 클러스터 리전과 인스턴스 유형을 나열하고, 가장 싼 선택지를 고르고, 그것을 1시간 온디맨드로 예약하는 정확한 명령을 보여 주되 실제로 예약하지는 않는다.
  • 통과 조건은 API에서 실시간 리전을 조회하고, 문서에서 현재 가격을 찾고, 유효한 예약 명령을 만드는 것이다. 무엇보다 유료 클러스터를 생성하면 안 된다.
  • 코드 검사는 GET /v1/compute/regions 호출이 200으로 성공했는지 본다. 이 요청 검사는 샌드박스 실행에서만 작동한다.
  • LLM 심판 루브릭은 공식 가격을 조회했는지, 지원되는 선택지를 비교했는지, 유효한 예약 명령을 만들었는지를 본다. 가격 근거가 없으면 실패로 처리하고, 헷갈리는 API 응답과 복구 시도도 기록하게 한다.
  • guard는 POST /v1/compute/clusters 요청을 막는다. guard는 에이전트가 일하는 동안 적용되고, 검사는 에이전트가 끝난 뒤 실행된다.

해석

사례 설정에서 눈여겨볼 축은 모델이 아니라 조건(skill 유무)이다. Together가 재고 싶은 것은 '어느 모델이 더 똑똑한가'보다 '우리가 만든 skill·문서가 에이전트 성공률을 얼마나 올리는가'로 보인다. 이 도구는 플랫폼 회사가 자사 문서·skill에 투자한 효과를 수치로 증명하는 수단에 가깝다.

실제 API를 건드리는 평가는 격리 실행이 전제다

사실 표

로컬 실행과 샌드박스 실행

구분로컬 실행샌드박스 실행
실행 위치내 컴퓨터의 임시 작업 공간에서 claude·codex CLI 실행(설정은 매번 초기화)실행마다 새 Together Sandbox. 샌드박스 자체는 네트워크 접근 없음
API 요청 검사·guard불가(요청을 보거나 막을 수 없음)가능(모든 요청이 Guardian을 거침)
키 노출에이전트가 사용자 권한으로 돌아 로컬 파일과 실제 키에 접근 가능샌드박스에 실제 키가 들어가지 않음(대체값을 받음)
권장 용도신뢰하는 과제의 빠른 시험복잡하거나 위험한 평가, 프로덕션 평가

출처 1 · Local runs / Sandboxed runs

사실
  • 샌드박스 실행을 시작하면 Hurdle이 로컬 프록시 Guardian을 띄우고, Together와 WebSocket 하나를 연다. Together는 그 실행용 샌드박스를 새로 부팅한다.
  • 에이전트가 여는 모든 연결은 그 소켓을 타고 Guardian으로 돌아오고, Guardian이 요청마다 허용하거나 거부한다. 차단된 요청에는 403으로 답하므로 요청이 사용자 API에 닿지 않는다.
  • 에이전트는 무작위 대체 키를 받는다. 에이전트가 API를 호출하면 Guardian이 실제 키로 바꿔 끼워 전달한다. 모델 제공사(Anthropic·OpenAI) 호출도 같은 경로로 간다.
  • 기본값에서는 샌드박스가 호출 가능한 엔드포인트를 제한하지 않는다. 그래서 평가 전용의 잔액이 적은 키를 쓰고 위험한 동작에는 guard를 걸라고 권한다.
  • Guardian은 키를 Authorization 헤더에만 넣어 준다. 다른 방식으로 키를 받는 API는 샌드박스 실행에서 인증되지 않는다.

출처 1 · Local runs

설명

구조의 요점은 실행 격리(Together 측 샌드박스)와 통제·키 관리(사용자 측 Guardian)를 나눈 데 있다. 샌드박스에는 자체 네트워크가 없고 모든 외부 호출이 사용자 컴퓨터의 Guardian을 거쳐 나간다. 그래서 요청 검사·차단·키 대체를 한 지점에서 할 수 있다. 그 대가로 외부 트래픽은 사용자 쪽 회선과 프로세스에 묶인다.

도입 문턱은 낮고, 번들 예제의 Together 쪽 비용은 실행당 1센트 미만이라고 한다

사실
  • 필요한 것은 Node.js 22.18 이상과 Claude Code 또는 Codex CLI다. npx hurdle init으로 시작하고, --agent codex로 Codex를 고른다.
  • 모델 쪽 인증은 Anthropic API 키, claude setup-token으로 받은 OAuth 토큰, OpenAI API 키 중 하나로 한다. 샌드박스를 쓰려면 Together API 키가 따로 필요하다.
  • 기본 예제는 파일 하나를 answer.txt로 복사하는 로컬 과제다. 샌드박스 예제는 Together에서 모델 목록을 조회하고 짧은 chat completion을 한 번 실행한 뒤 응답을 저장한다.
  • hurdle setup은 자격 증명을 확인하고, Guardian을 설치하고(현재 macOS·Linux만), 프로젝트를 Together 샌드박스 실행으로 설정한다.
  • 번들 샌드박스 예제를 돌리려면 샌드박스와 chat completion에 쓸 Together 크레딧이 필요하다. 그 예제의 실행당 Together 쪽 비용은 1센트의 일부 수준일 것이라고 한다. 더 긴 실제 과제의 비용은 밝히지 않았다.
  • 처음 시작할 때는 사용자가 이미 에이전트에 맡기는 과제 하나를 고르라고 권한다. 이를 최고 모델과 한 단계 아래 모델로 각각 몇 번씩 반복해 돌리라고 한다. 한 번의 실행은 우연히 통과하거나 실패할 수 있어서다.

출처 1 · Try it yourself / Find your own hurdles

해석

'1센트 미만'은 짧은 번들 예제를 돌릴 때의 Together 쪽 비용일 뿐이다. 실제 과제에서는 에이전트 모델 토큰과 hybrid 판정에서 실행마다 붙는 심판 모델 호출이 비용의 큰 몫을 차지할 가능성이 높다(추정). 사례 suite 하나만 해도 60회 실행에 Opus급 심판 호출이 60회 따라붙는다. 글은 이 모델 비용을 수치로 밝히지 않고, 뷰어가 실행당 평균 비용을 보여 준다고만 적었다.

근거는 어디서 왔나

사실
  • 근거는 Together 사내 경험이다. 지난봄 평가를 시작했고, 6개월 동안 도구를 만들었고, 6월에 두 모델로 시험했다.
  • 글 본문에는 통과율·소요 시간·비용 같은 Together 자체 평가 결과가 수치로 나오지 않는다. 결과 화면은 그림 두 장으로만 실렸다.

출처 1 · 도입부 / The eval suite / Run and view results

해석

설계와 명령어는 GitHub 오픈소스로 독자가 직접 검증할 수 있다. 반면 'skill을 붙이면 성공률이 오른다'처럼 이 도구의 가치를 보여 줄 결과는 공개되지 않았다(그림 속 수치는 확인하지 못함). 효과에 대한 주장은 아직 검증되지 않은 상태로 보는 것이 맞다.

누가 득을 보고 누가 손해를 보는가

사실
  • 글이 지목한 사용자는 개발자 대상 제품을 만드는 회사, 곧 API·SDK·문서를 제공하는 쪽이다.
  • 지원하는 에이전트 러너는 Anthropic의 Claude Code와 OpenAI의 Codex뿐이다. 사례의 모델과 심판 모델은 모두 Claude 계열이다.
  • 격리 실행 인프라는 Together Sandbox API이고, 샌드박스 실행에는 Together 크레딧이 든다.

출처 1 · How Hurdle works / The eval suite / Sandboxed runs

해석
  • Together AI: 득. 도구는 무료지만 안전한 평가 경로가 Together Sandbox로 이어진다. 그래서 다른 개발자 플랫폼 회사를 샌드박스·크레딧 고객으로 들이는 입구가 된다. 다만 글이 밝힌 실행당 비용은 짧은 예제 기준의 1센트 미만뿐이어서 직접 매출 규모는 가늠하기 어렵다. 직접 매출보다는 계정 확보와 브랜드 효과에 가깝다고 본다. 확신 중간.
  • Anthropic·OpenAI: 소폭 득. 평가가 반복 실행과 LLM 심판을 전제하므로 토큰 소비가 늘어나는 구조다. 두 회사의 에이전트가 사실상 평가 표준 러너로 굳어지는 효과도 있다. 규모는 글로 가늠할 수 없다. 확신 낮음.
  • API 품질이 약한 개발자 플랫폼: 상대적 손해 가능성. 에이전트 성공률이 측정되기 시작하면 문서·인증 방식(예: Authorization 헤더가 아닌 인증)의 약점이 수치로 드러난다. 다만 글은 특정 기업을 지목하지 않는다. 확신 낮음.

비판적으로 다시 읽기

해석
  • 이해관계: Together는 Sandbox API와 GPU 클러스터를 파는 회사다. 글이 권하는 '복잡하거나 위험하면 반드시 샌드박스'는 안전 조언인 동시에 자사 상품으로 가는 경로다. 로컬 실행을 요청 검사·guard가 안 되는 반쪽 모드로 둔 설계도 같은 방향을 가리킨다.
  • 범위의 한계: 러너가 Claude Code·Codex 둘뿐이다. 글이 처음에 강조한 '대표성 있는 모델·하니스 표본'과는 거리가 있다. 다른 에이전트 하니스를 쓰는 개발자층의 경험은 이 도구로 잴 수 없다.
  • 측정의 한계: hybrid 판정의 절반은 LLM 심판이다. 심판 모델이 피평가 모델과 같은 계열(사례에서는 Opus 4.8이 Opus 4.8을 채점)일 때 생기는 편향을 글은 다루지 않는다. 15회 반복이 통과율 차이를 구분하기에 충분한지도 근거가 없다.
  • 안전 기본값: 기본값에서는 엔드포인트를 제한하지 않는다. 비용이 큰 행동은 사용자가 guard를 빠짐없이 써야 막힌다. 그래서 '잔액 적은 전용 키' 같은 운영 수칙에 기대게 된다.
  • 운영 제약: Guardian은 현재 macOS·Linux만 지원하고, 키를 Authorization 헤더로만 넣어 준다. 모든 트래픽이 사용자 컴퓨터를 거치므로, 대규모 병렬 평가나 CI 환경에서 어떻게 확장되는지는 글에 없다.

작성자의 생각

해석
  • 동의: 에이전트가 API의 주 사용자가 되는 흐름에서 '과제 + 조건 + 반복 + 통과율'로 에이전트 경험을 재는 틀은 맞는 방향이다. 특히 skill·MCP 유무를 조건으로 놓고 A/B 비교하는 설계는 문서 투자 효과를 정량화하는 실무 도구로 쓸모가 있다.
  • 다르게 보는 점: 이 글의 무게는 기능보다 아키텍처에 있다. 샌드박스에서 실행하고, 로컬 프록시로 통제하고, 키를 바꿔 끼우는 구조는 평가 도구보다 '에이전트를 실제 자격 증명과 함께 안전하게 돌리는 실행 환경'의 원형에 가깝다. 이 구조가 평가를 넘어 운영 단계로 쓰임이 넓어질 때 Together의 샌드박스 사업에 의미가 생긴다고 본다. 확신 낮음.
  • 원문을 직접 읽을 가치: API를 파는 조직의 플랫폼·DevRel 책임자라면 suite 설계와 Sandboxed runs 절은 읽을 만하다. 투자 판단 목적이라면 이 리포트로 충분하다.

투자자 관점의 정리

해석
  • 확인된 것: Together는 Sandbox API를 제품으로 제공하고, Hurdle의 안전한 평가 경로(샌드박스 실행)를 그 위에 얹었다. 무료 오픈소스 도구로 샌드박스 수요를 만드는 개발자 퍼널 전략으로 해석한다(해석, 확신 중간).
  • 새로 나온 것: '에이전트 경험'을 반복 측정하는 도구가 플랫폼 회사 손에서 나왔다. 개발자 도구 시장의 평가 기준이 '사람이 읽기 쉬운 문서'에서 '에이전트가 통과하는 과제 비율'로 옮겨 가는 신호로 읽힌다. 실적 추정에 반영할 단계는 아니다. 확신 낮음.
  • 답하지 않은 것: 자사 평가 결과(skill 효과, 모델 간 차이), Sandbox 사용량과 가격, 실행당 모델 토큰 비용. 따라서 Together의 매출이나 밸류에이션 전제에 넣을 수치는 이 글에서 나오지 않는다.
  • 종목 판정: 원문에 등장하는 회사는 Together AI, Anthropic, OpenAI다. 원문은 상장 여부·주가·상장 종목을 다루지 않는다. 상장 종목에 대한 근거가 없으므로 상장 종목 판정은 하지 않는다. 회사 단위로는 Together AI를 약한 호재로, Anthropic·OpenAI를 중립에 가까운 약한 호재로 본다(근거는 앞 절). 확신 낮음.
  • 다음에 확인할 것: GitHub 저장소의 채택 지표(별·기여자·지원 러너 확대 여부), Together가 Hurdle 결과를 공개 벤치마크로 내는지 여부, Sandbox API 가격·사용량 공개, Guardian의 인증 방식·OS 지원 확대. 러너가 Claude Code·Codex 밖으로 넓어지고 다른 플랫폼 회사가 결과를 공개하기 시작하면 '측정 표준' 가설의 확신을 올린다.
