심층 분석 · 글 분석

Anthropic : 코드 작성이 아니라 검증이 병목이다 — 운영 중인 API를 검증기로 삼아 Messages API를 Rust로 옮겼다

해석 Anthropic은 운영 중인 Python API를 정답 기준(오라클)으로 삼고, 에이전트가 세 겹의 검증 루프 안에서 차이를 고치게 하는 방식으로 Messages API를 Rust로 옮겼다. 요청당 CPU 약 70% 절감이라는 결과보다, 대형 마이그레이션의 비용 구조가 '작성'에서 '검증 신호 설계'로 옮겨 갔다는 주장이 이 글의 핵심이다. 수치는 모두 회사 내부 자료이고 외부에서 검증할 수 없다.

주장 한 줄

해석

Claude가 코드를 충분히 빨리 쓰는 지금, 운영 중인 시스템을 옮기는 일의 병목은 검증이다. 테스트로 '정답'을 다 정의할 수 없는 시스템이라면 운영 중인 시스템 자체를 검증기로 만들고, 그 신호 위에서 에이전트가 스스로 고치게 하면 된다는 것이 이 글이 설득하려는 내용이다. Messages API의 Rust 이전은 그 사례로 제시된다.

트래픽이 1,800배 늘면서 '요청 전달기'였던 Python 서비스가 한계에 닿았다

사실
  • Messages API는 외부 고객과 Claude Code·Cowork 같은 자사 앱이 Claude에 접근하는 주 경로다.
  • API 트래픽은 2024년 초부터 2026년 가을까지 약 1,800배 늘었다. 트래픽 증가를 보여 주는 그림 1은 자사 플랫폼의 일평균 요청 수(자사 사용 포함)를 월평균한 것이다.
  • 2023년 Python으로 처음 만들 때는 요청을 모델에 넘기고 답을 돌려주는 단순한 서비스였다. 당시 한 엔지니어는 '사실상 요청 전달기'라고 불렀다.
  • 2025년 말에는 모든 요청이 검증 → 프롬프트 변환 → 토큰화 → 안전 분류기 심사를 거쳤다. 출력 쪽에서는 토큰 스트림을 텍스트·thinking·tool call로 나눠야 했고, Python은 객체 생성·메모리 해제·작업 전달마다 오버헤드를 더했다.
  • 리서치·추론 팀이 소유한 Python 라이브러리와 의존성이 얽혀 있어 다른 언어로 옮기려면 로깅·지표·도구를 다시 만들어야 했다.

출처 1 · 도입부, Why migrate?

AI 가정

'2024년 초 → 2026년 가을'을 2.5~2.75년으로 본다. 원문에는 정확한 시작·끝 월이 없다.

계산

1,800배를 연율로 환산하면 매년 약 15~20배 늘어난 셈이다. 같은 기간 서비스 구조를 손대지 않았다면 요청당 CPU 효율이 그대로인 채 CPU 수요가 같은 속도로 늘었다는 뜻이다.

사실
  • 표준적인 처방대로 모델 출력 파싱 코드만 Rust로 다시 짜서 Python에서 호출했다. API의 CPU 사용량은 약 8~10% 줄었다.
  • 그 대가로 토큰 하나가 Python과 Rust 사이를 세 번 오가게 되어 새 오버헤드가 생겼고, 이득이 늘어난 복잡도를 정당화하지 못했다고 평가한다.
  • 2024년에는 Go나 Rust로 옮기자는 제안이 나왔다가 내부에서 일단 기각됐다.

출처 1 · Incremental or all at once?, 도입부

기존 테스트 700개로는 이번 이전을 믿을 수 없었다

사실
  • '정답'을 정의하는 길을 셋으로 나눈다. 규칙(Lean 같은 증명 보조기), 예시(테스트. Bun이 Zig에서 Rust로 옮길 때 TypeScript 테스트가 두 버전을 함께 판정한 경우), 기존 시스템을 오라클로 쓰는 것이다. Anthropic은 앞의 둘로 부족해 세 번째를 택했다.
  • 기존 통합 테스트는 약 700개였다. 테스트가 Python API를 테스트 프로세스 안에서 돌리고 과금·속도 제한 서비스를 Python 메모리 안에서 흉내 내는 구조여서, 코드와 함께 테스트도 옮겨야 했다.
  • 옮긴 테스트를 감사하자 약해진 assertion이 100개 넘게 나왔다. 테스트 통과가 코드가 맞다는 뜻인지, 틀린 코드가 통과하도록 테스트가 바뀌었다는 뜻인지 가릴 수 없게 된 것이다.
  • 기능 조합은 전수 시험이 불가능하다. 이진 옵션 20개만으로 100만 가지가 넘고, 건당 1초로 잡아도 모델 하나에 12일이 걸린다.
  • 이전 기간 내내 Python API에 새 모델·기능이 계속 들어가서 기준점이 움직였다. 또 Claude의 응답이 비결정적이라 출력이 다르다고 버그라는 보장이 없고, 고객 요청을 읽을 수 없어 어디서 갈렸는지도 쉽게 볼 수 없었다.

출처 1 · General approaches, Tests

운영 트래픽을 '그림자'로 돌려 차이의 모양만 기록했다

사실
  • 4월에 Rust API는 테스트를 약 98% 통과했지만, 운영 트래픽에서 입력이 Python과 일치한 비율은 약 4분의 1이었다.
  • 차이의 원인 가운데 하나는 테스트가 다루지 않은 경우였다. 예컨대 Python은 JSON tool call을 쓸 때 이모지 같은 문자를 이스케이프하는데 Rust는 그대로 써서 프롬프트가 몇 바이트 달라졌다.
  • 운영 트래픽에서는 흔한 버그 하나가 해당 요청마다 나타나서 불일치 다수를 만든다. 테스트에서는 각 경우가 한 번씩만 집계된다.
  • 일치율 그림은 비교 대상이 시기마다 달랐고, 오해를 부르는 6일을 뺐다고 캡션에 적혀 있다.

출처 1 · Detecting parity with production

  • 요청이 고객 한도·과금에 한 번만 잡히도록 하고, 비결정성을 피하려고 모델은 한 번만 돌린 뒤 그 출력을 Rust에 재생(replay)했다.
  • Claude는 거의 어떤 프롬프트도 받아들이므로, 작은 편차는 오류 없이 답만 바꾼다. 그래서 모델 호출 전후의 모든 단계가 정확히 일치해야 했다.
  • 프라이버시 때문에 요청과 응답 텍스트는 보지 않고 차이의 모양만 기록했다. 체크포인트는 단계별(수락/거절 → 설정 해석 → 프롬프트 생성)·프롬프트 조각별로 비교해 처음 갈린 지점을 찾는다. 핑거프린트는 처음 달라진 바이트 위치와 두 버전의 길이 차를 기록한다.
  • 같은 버그는 영향을 주는 모든 요청에 같은 핑거프린트를 남기므로 핑거프린트별로 묶어 우선순위를 정했다. 앞쪽 차이를 고치자 가려져 있던 다른 차이가 새 핑거프린트로 드러나기도 했다.

출처 1 · Detecting parity with production

설명

일반적인 diff·섀도잉 도구는 같은 요청을 두 번 돌려 저절로 달라지는 부분을 무시 목록에 넣는다. 응답이 매번 달라지는 LLM 서비스에 이 방식을 쓰면 응답 전체가 무시 대상이 되고 그 안의 버그도 함께 묻힌다. 모델 출력을 한 번 만들어 양쪽에 재생한 것이 이 설계의 핵심이다.

에이전트는 세 겹의 루프 안에서 스스로 고쳤고, 사람은 경계에서 판단했다

사실
  • 버그 하나가 거의 같은 기록을 수십만 건 만들 수 있었다. 스크립트가 10~30분마다 기록을 다른 필드 기준으로 묶고, 새 종류가 보일 때만 조정 에이전트를 깨웠다. 조정 에이전트는 종류마다 작업 에이전트를 배정하고 공용 Slack 채널에 스레드를 열었다.
  • 4월 초기 방식에서는 가설 하나마다 PR 리뷰와 스테이징 배포가 필요해 피드백에 몇 시간에서 며칠이 걸렸다.
  • 재설계한 내부 루프에서는 에이전트가 두 코드베이스가 다 있는 클라우드 샌드박스에서 일했다. 입력 검사는 모델을 부르지 않고 양쪽이 만들 프롬프트를 비교해 1초 안에 끝났고, 출력 검사는 가짜 모델의 각본 응답을 양쪽에 통과시켰다.
  • 에이전트는 핑거프린트만 보고 원인을 추정했다. 그 차이를 재현하는 요청이나 응답을 직접 쓰고, 양쪽이 같아질 때까지 Rust를 고친 다음 옛 코드에서 실패하고 새 코드에서 통과하는 테스트를 추가했다.

출처 1 · Verification loops, Inner loop

  • 내부 루프에서 외부 루프로 넘어가려면 PR 리뷰를 거쳐야 했다. 엔지니어는 추측이 아니라 제안된 수정과, 그 차이가 버그인지 의도된 변경인지처럼 검증기가 답하지 못하는 질문에 집중했다.
  • 5월 중순 남은 큰 차이 가운데 하나는 웹 검색 도구 설명이 빠진 것이었다. 운영 API는 이 설명을 내부 서비스에서 받아 오는데 Rust는 아직 그 서비스를 부르지 않았다. 에이전트가 설명 텍스트를 파일로 복사하자고 제안했고 로컬 검증기는 통과했지만, 엔지니어가 출시 전에 버려질 임시방편이라며 거절했다.

원문

출처 1 · Inner loop

사실
  • 외부 루프는 수정 전후의 Rust 빌드를 운영 섀도 트래픽에서 비교했다. 텍스트 대신 모델, prompt caching·tools·extended thinking 사용 여부 같은 요청 속성을 기록해 같은 종류의 요청끼리 핑거프린트 빈도를 비교했다. 핑거프린트가 사라지지 않으면 과제는 내부 루프로 돌아갔다.
  • 메모리 루프는 리뷰에서 나온 교정을 이후 모든 에이전트에 적용했다. 웹 검색 사례에서는 결정·이유·올바른 수정을 메모로 남겼고, 서비스 호출을 만드는 데 몇 주가 걸리는 동안 새 핑거프린트로 나타난 같은 버그 기록을 에이전트들이 그 메모에 연결했다.
  • 'Python이 한 일을 그대로 옮긴다'는 규칙을 만든 뒤, 한 에이전트가 기존 포팅에서 추측에 기댄 곳 7군데를 더 찾았다. 6월에는 리뷰 코멘트 약 60개를 묶어 규칙안을 만들었고, 엔지니어가 다듬어 CLAUDE.md에 반영했다.
  • 교훈 일부는 영구 검사가 됐다. Rust가 Python에서 벗어나면 실패하는 테스트, 리뷰어가 반복 지적한 패턴을 막는 lint, 그리고 Python을 바꾸면 Rust도 함께 바꾸거나 예외를 신청하게 하는 병합 검사다.

출처 1 · Outer loop, Memory loop

결과: 서비스 중단·기능 동결 없이 요청당 CPU 약 70% 절감, 첫 토큰까지 시간 중앙값 약 20% 단축

사실
  • Rust API는 요청당 CPU를 약 70% 덜 쓰고(같은 CPU로 약 3.3배 요청 처리), 첫 토큰까지 시간(TTFT) 중앙값을 약 20% 줄였다. 이전 기간 동안 서비스를 내리거나 기능 개발을 멈추지 않았다.
  • 측정 범위는 지표마다 다르다. CPU는 한 리전, 메모리는 운영 전체, TTFT는 고객의 Claude Code 요청을 더 짧은 기간 측정한 값이다. TTFT 그림에서는 첫 측정점 이전의 하락이 요청 거의 전부가 아직 Python에 있을 때 일어났다고 캡션이 밝힌다.
  • 요청은 몇 번에 나눠 Rust로 넘겼고, 공개 트래픽은 2026년 9월에 Rust로 이전됐다. 4월부터의 2주 단위 병합 건수 그림에는 이전과 무관한 변경도 섞여 있다.

부분 재작성(8~10%)과 전면 이전(약 70%)의 차이가 이 글의 실질적인 경제성 논거다. 언어 경계를 넘는 비용을 없애야 효과가 났다는 뜻으로 읽힌다. 다만 70%는 API 계층의 CPU이고 GPU 추론 비용이 아니다. 원문은 전체 서빙 비용에서 이 CPU가 차지하는 비중을 밝히지 않아 총원가 영향은 판단할 수 없다(확신 중간).

출처 1 · Looking ahead, Lessons learned

비판적으로 다시 읽기

해석
  • 말하는 자리: 이 글은 Claude의 에이전트 코딩 능력을 보여 주는 자사 사례다. '대형 이전이 이제 정당화된다'는 결론은 Claude Code 같은 상품 수요와 직결된다. 방법론은 설득력이 있지만 결론의 일반화는 이해관계를 감안해 읽어야 한다.
  • 빠진 비용: 에이전트가 쓴 연산량과 비용, 투입 엔지니어 수, 이전 기간(4월 → 9월, 약 5개월)에 나온 장애나 고객 영향이 없다. '작성은 싸졌다'는 주장의 핵심 반대 근거가 비어 있다.
  • 일반화의 전제: 이 방식은 운영 트래픽이 충분히 많고 다양해야 하고, 기존 시스템을 오라클로 쓸 수 있으며, 모델 출력을 재생할 수 있는 구조여야 성립한다. 트래픽이 적거나 부작용(결제·쓰기)이 핵심인 시스템에는 그대로 옮기기 어렵다.
  • 수치의 기준: TTFT 20%는 고객 Claude Code 요청만 더 짧은 기간 잰 값이다. 그림 캡션에 따르면 개선 폭은 첫 점에서 둘째 점까지의 변화이고, 첫 점 이전의 하락은 요청 거의 전부가 아직 Python에 있을 때 일어났다. 따라서 그 하락은 20%에 들어가지 않는다. 다만 이전 기간에도 Python 쪽 기능 변경이 계속됐으므로, 두 점 사이 개선분이 모두 언어 이전 덕인지는 원문만으로 가를 수 없다(확신 낮음). CPU 70%도 한 리전 측정이다.
  • 1,800배는 API 트래픽 전체의 증가이고, 이 API는 Claude Code·Cowork 같은 자사 앱도 쓴다(도입부. 그림 1 캡션도 자사 사용 포함이라고 밝힌다). 외부 고객 수요의 증가율로 그대로 읽으면 안 된다.
  • 글 스스로 보여 준 위험: 검증기를 통과한 임시방편(웹 검색 사례)과 약해진 assertion 100개 이상은, 에이전트가 신호를 가장 싸게 맞추는 방향으로 최적화한다는 증거다. 사람 리뷰라는 관문이 빠지면 같은 방식이 오히려 위험해진다.

작성자의 생각

해석
  • 동의하는 부분: 대형 재작성의 제약이 작성 비용에서 검증 비용으로 옮겼다는 진단은 사례가 구체적이라 신뢰도가 높다. 테스트 98% 통과와 운영 일치 약 25%가 동시에 나온 대목이 이를 잘 보여 준다(확신 높음).
  • 실무적으로 가치 있는 것은 결과 수치보다 설계 요소다. 텍스트를 보지 않고 차이의 위치·크기만 남기는 핑거프린트, 비결정성을 피하는 출력 재생, 교정을 규칙·테스트·병합 검사로 굳히는 메모리 루프는 다른 조직도 가져다 쓸 수 있다. 원문을 직접 읽을 가치가 있다.
  • 다르게 보는 부분: '사람은 경계로 물러난다'는 결론은 아직 이 사례 하나에서 나온 것이다. 본문 사례를 보면 무엇이 정답인지(버그인가 의도된 변경인가, 임시방편인가)를 판단하는 일은 여전히 사람이 했고, 그 판단의 양이 줄었다는 수치는 제시되지 않았다(확신 중간).

투자자 관점의 정리

해석
  • 확인된 것: LLM 서비스의 API 계층에서 언어 이전만으로 요청당 CPU를 약 70% 줄일 여지가 있었다. 트래픽이 연 15~20배(추정) 속도로 느는 서비스에서 서빙 계층 효율은 원가 관리 수단이다. 다만 GPU 추론 원가 대비 비중이 공개되지 않아 Anthropic 마진 추정에 반영할 근거는 없다(확신 낮음).
  • 새로 나온 것: 에이전트 코딩의 가치가 '코드를 빨리 쓴다'에서 '검증 신호가 있는 대형 작업을 맡긴다'로 확장된다는 주장이다. 사실이라면 레거시 이전·현대화 작업의 단가와 기간 전제가 바뀐다. 다만 근거는 Anthropic 자사 사례 하나뿐이다(확신 중간).
  • 답하지 않은 것: 에이전트 연산 비용, 장애 여부, 투입 인력이 없다. 최종 일치율도 본문 텍스트에는 없다(그림 6은 미확인). 이 방식의 경제성을 비교할 수 없으므로 '이전 비용이 얼마나 내려갔나'는 여전히 미지수다.
  • 종목 판정: 원문과 데스크 기록에 Anthropic의 상장 여부·주가 자료가 없어 종목 판정은 하지 않는다. 회사 차원에서는 자사 서빙 원가와 Claude Code 사용자 경험(TTFT)이 나아진 것이라 방향은 긍정적이지만 강도는 약하다(확신 낮음). 원문은 상장사·업종을 지목하지 않는다. 그래서 CPU 공급사(요청당 CPU 절감)나 IT 서비스·시스템 통합 업체(이전 작업의 자동화)에 미칠 영향은 짐작은 가능해도 근거가 없어 판정하지 않는다.
  • 다음에 확인할 것: 다른 기업이 운영 트래픽 오라클 방식으로 대형 이전을 끝냈다는 공개 사례가 나오는지, Anthropic이 에이전트 비용과 인력 투입을 밝히는지, Claude Code 쪽에서 '이전 작업'이 상품 기능으로 묶여 나오는지. 앞의 두 가지가 확인되면 '검증이 병목'이라는 주장을 일반 명제로 볼 수 있다.
