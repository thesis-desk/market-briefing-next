Google AI 블로그 : Gemini API가 도구 스키마를 필요할 때만 불러와 대규모 에이전트의 입력 토큰과 선택 오류를 줄인다

해석 Gemini Interactions API에 도구 스키마 지연 로딩(Tool Retrieval)이 프리뷰로 들어왔다. 도구 수십~수백 개를 붙인 에이전트의 비용·정확도 문제를 겨냥한 기능이지만 절감 폭이나 정확도 수치는 하나도 제시하지 않았다. 투자 판단을 바꿀 사건이라기보다 Google이 개발자를 Interactions API로 모으려는 플랫폼 정비로 읽힌다. Alphabet에는 중립에 가까운 약한 호재로 보며, 확신은 낮다.

주장 한 줄

사실

에이전트가 매 요청마다 전체 도구 라이브러리를 보내지 말고, 도구의 이름과 설명만 둔 채 파라미터 스키마는 필요할 때 불러오게 하라는 주장이다. 이렇게 하면 에이전트 규모가 커져도 입력 토큰을 줄이고 도구 선택 정확도를 유지할 수 있다고 한다. 다만 글은 이를 설계 목표('designed to')로 적었을 뿐 수치로 입증하지 않았다. 기능은 2026-11-19부터 Gemini Interactions API에서 프리뷰로 제공된다.

출처 1 · 도입부

도구가 늘수록 전체 스키마 전송은 토큰·지연·선택 정확도를 함께 깎는다

사실
  • 에이전트에 도구가 수십~수백 개 연결되면 요청마다 모든 파라미터 스키마를 보내는 부담이 빠르게 커진다.
  • 부작용은 세 가지로 제시된다. 입력 토큰 증가, 지연 증가, 후보 목록이 길어질수록 떨어지는 도구 선택 정확도다.
  • 해법은 전체 도구 라이브러리를 대기 상태로 두고, 현재 작업에 필요한 스키마만 불러오는 것이다.

출처 1 · 도입부

이름·설명은 늘 보이고, 스키마는 같은 요청 안에서 불러온다

사실
  • 요청에 tool_search 도구를 추가하고, 미뤄 둘 도구에 defer_loading: true를 단다.
  • 미뤄 둔 도구도 이름과 설명은 모델에 보인다. 컨텍스트에서 빠지는 것은 파라미터 스키마뿐이다.
  • 모델이 도구를 이름으로 요청하면 API가 전체 스키마를 불러오고, 모델이 함수를 호출한다. 이 과정이 모두 한 번의 요청 안에서 끝난다.
  • 세 단계(tool_search_call → tool_search_result → function_call)는 interaction.steps에 남는다. 그래서 모델이 어떤 도구를 검토했는지 디버깅할 때 볼 수 있다.
  • 예시는 50개가 넘는 함수를 미뤄 두고, 자주 쓰는 도구는 미루지 말라고 권한다. 예시 모델명은 gemini-4-hydrogen이다.
  • 검색은 Gemini 서버에서 돈다. 개발자가 인덱스를 만들거나 호스팅할 필요가 없고, 코드에서 바꿀 것은 새 도구 하나와 플래그뿐이다.

출처 1 · How it works

해석

모델은 이름과 설명만 보고 어떤 도구를 불러올지 고른다. 그러면 도구 설명의 품질이 선택 정확도를 좌우하는 변수가 된다. 글이 steps 기록을 '도구 이름이나 설명을 디버깅할 때' 쓰라고 소개한 것도 이 부담을 개발자에게 넘긴다는 뜻으로 읽힌다.

프리픽스 캐시를 깨지 않고 원격 MCP 서버에도 그대로 적용된다

사실
  • 미뤄 둔 스키마는 프롬프트 앞부분에 들어가지 않는다. 모델이 불러온 스키마는 대화 뒤쪽에 덧붙는다. 그래서 캐시된 프리픽스가 턴마다 바뀌지 않는다.
  • Gemini API의 원격 MCP 서버 도구(mcp_server)에 defer_loading: true를 달면 그 서버가 노출하는 모든 도구를 필요할 때 불러온다. 큰 MCP 서버도 도구를 하나씩 나열하지 않고 연결할 수 있다.

출처 1 · How it works

해석

실무에서 더 중요한 것은 캐시 호환일 수 있다. 도구를 동적으로 바꾸는 방식은 대개 프롬프트 앞부분을 흔들어 캐시 적중을 깨는데, 불러온 스키마를 뒤에 붙이는 설계로 이 충돌을 피했다. 다만 캐시 할인율이나 적중률 변화는 글에 없어 효과의 크기는 알 수 없다.

자체 레지스트리가 있으면 클라이언트 쪽 검색으로 돌릴 수 있다 — 대가는 검색마다 왕복 1회

출처 1 · How client-side retrieval works

해석

클라이언트 모드는 사용자별 권한 필터를 직접 거는 기업 고객을 겨냥한 장치로 보인다. 도구 목록과 권한 판단을 Google 서버에 넘기지 않아도 되므로, 보안 요구가 큰 고객에게 채택 장벽을 낮춘다.

별도 요금은 없고, 절감 여부는 각자의 트래픽에 달렸다

사실
  • Tool Retrieval에는 별도 요금이 없다. 입출력 토큰은 호출한 모델의 표준 요금으로 청구된다.
  • tool_search를 켜면 작은 고정 분량의 입력 토큰이 추가된다.
  • 모델이 불러온 스키마는 처음부터 선언한 도구와 똑같이 이후 대화 내내 입력으로 청구된다.
  • 지원 범위는 Interactions API에서 Gemini 3.6 이후 모델이며, 모든 Gemini 4 모델을 포함한다.

해석

손익분기 조건은 단순하다. 고정 오버헤드와 검색 단계의 비용보다, 불러오지 않은 스키마로 아낀 입력이 커야 한다. 도구가 적거나 대부분을 매번 쓰는 에이전트에는 오히려 손해일 수 있다. 검색 단계가 만드는 출력 토큰과 지연에 대해서도 글은 아무것도 말하지 않는다. Google 스스로 '측정해 보라'고 단서를 달았으니 절감은 보장이 아니라 조건부 주장으로 봐야 한다.

근거가 어디서 왔나

사실
  • 근거는 Google의 자사 제품 발표와 API 사용 예시(요청 코드, steps 출력 형식)뿐이다.
  • 토큰 절감률, 지연 변화, 도구 선택 정확도에 대한 수치·벤치마크·고객 사례는 없다.

출처 1

설명

독자가 직접 검증할 수 있는 부분은 API 동작이다. 문서와 프리뷰 API로 defer_loading 동작, steps 기록, 캐시 프리픽스 유지 여부를 확인할 수 있다. 반면 '정확도를 유지한다'는 효과 주장은 Google 내부 평가에 기댄 것으로 보이는데, 그 평가조차 공개되지 않았다.

누가 득을 보고 누가 손해를 보는가

사실
  • 글이 수혜 대상으로 지목하는 것은 기업이 아니라 사용자 유형이다. 도구 수십~수백 개를 붙인 에이전트 개발자, 큰 원격 MCP 서버를 연결하려는 개발자, 자체 도구 레지스트리나 사용자별 권한 필터를 운영하는 개발자가 그들이다.
  • 특정 상장사의 수혜나 피해, 경쟁사와의 비교는 글에 없다.

출처 1

비판적으로 다시 읽기

해석
  • 전제 1 — 이름과 설명만으로 모델이 올바른 도구를 찾아낸다는 가정이다. 비슷한 이름의 도구가 많은 실제 라이브러리에서는 검색 단계가 새로운 오류의 원천이 될 수 있다. 글은 '정확도가 유지된다'를 설계 의도로만 말한다.
  • 전제 2 — 큰 라이브러리에서는 대부분의 스키마를 불러오지 않는다는 가정이다. 한 대화 안에서 여러 도구를 연달아 부르는 장기 작업 에이전트라면 불러온 스키마가 쌓여 절감 폭이 줄어든다.
  • 빠진 반대 근거 — 지연 수치가 없다. 서버 쪽 검색도 모델이 한 번 더 판단하는 단계이므로, 한 요청 안에서 끝난다는 사실이 곧 지연이 없다는 뜻은 아니다.
  • 이해관계 — 글쓴이는 해당 API를 만들고 파는 Google이다. 기능이 Interactions API와 Gemini 3.6 이후 모델로 한정된 점에서 보듯, 개발자를 최신 API와 모델로 옮기려는 의도가 함께 있다. '프리뷰'인 만큼 인터페이스와 과금 조건은 바뀔 수 있다.

덧붙임 · 투자자 관점 여기까지가 누구의 관점도 넣지 않은 공통 본문입니다. 아래는 밸류에이션과 투자 판단을 담은 덧붙임이며, 해석과 가정이 중심입니다.

투자자 관점의 정리

해석
  • 확인된 것 — Google은 에이전트 플랫폼의 운영 문제(도구 폭증, 캐시, MCP 연결)를 API 차원에서 풀어 주는 쪽으로 Gemini API를 다듬고 있다. 기능 자체는 경쟁력 유지를 위한 기본기에 가깝다. 확신 중간.
  • 답하지 않은 것 — 절감률, 정확도, 지연 수치가 전혀 없다. 이 기능이 실제로 개발자의 모델 선택을 바꿀 만큼의 차이를 만드는지는 이 글만으로 판단할 수 없다. 다음 확인 지점은 Google이나 고객이 공개하는 정량 결과, 그리고 프리뷰 이후 정식 제공 시점과 과금 조건의 변화다.
  • 실적 추정에 대한 뜻 — 별도 요금이 없고 목적이 입력 토큰 절감이므로, 큰 도구 라이브러리를 쓰는 고객의 요청당 토큰 매출은 단기적으로 줄어드는 방향이다. Google은 이를 에이전트 사용량 확대와 Interactions API로의 고객 이전으로 메우려는 것으로 보인다. 이번 글이 클라우드·AI 매출 추정을 바꿀 근거는 되지 않는다. 확신 중간.
  • 위험 — 기능이 Interactions API에서 Gemini 3.6 이후 모델로만 제공된다. 이전 API나 구형 모델에 묶인 고객에게는 혜택이 없다. 그래서 채택 속도는 Interactions API 자체의 보급에 달려 있다. 확신 낮음.
  • Alphabet(Google) — 중립에 가까운 약한 호재, 확신 낮음. 근거는 에이전트 개발 편의와 기업 고객용 클라이언트 모드가 Gemini API의 개발자 유인을 다소 높인다는 점이다. 요청당 토큰 매출 감소와 상쇄되므로 강도는 약하다. 정량 결과가 공개돼 경쟁 API 대비 정확도·비용 우위가 확인되면 호재 쪽으로 강해진다. 프리뷰가 길어지거나 실사용 정확도 문제가 보고되면 중립으로 내린다. 주가·배수 자료는 원문에 없어 반영 정도는 판단하지 않는다.
  • 다른 모델 제공사, MCP 서버 제공사, 에이전트 플랫폼 기업 — 원문에 언급이 없어 판정하지 않는다.
