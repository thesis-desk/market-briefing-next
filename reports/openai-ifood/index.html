심층 분석 · 글 분석

OpenAI : iFood는 에이전트 자동화의 병목을 모델이 아닌 실행 런타임으로 보고, 1만5천 개 저장소에 REST API 하나로 코딩 에이전트를 돌린다

해석 OpenAI가 낸 고객 사례 홍보 글이다. 새로 얻을 정보는 대기업 고객이 패키지 제품 대신 원시 API 위에 사내 에이전트 런타임을 직접 지었다는 사용 방식에 있다. 공개된 수치(2만5천 건, 270억 토큰, 건당 4센트)를 결합하면 건당 약 100만 토큰, 총지출 약 1천 달러가 나온다. 토큰 사용량은 크지만 OpenAI 매출에서 차지하는 비중은 미미한 단계로 읽힌다.

주장 한 줄

사실

에이전트 자동화를 막는 것은 지능이나 사용 사례가 부족해서가 아니라 공용 실행 인프라(런타임)가 없어서라고 본다. iFood는 이 런타임을 REST API로 열었고, 그 결과 1만5천 개 이상의 저장소에서 반복 작업을 규모 있게 위임할 수 있게 됐다는 것이 글의 요지다.

출처 1 · The challenge isn’t the task—it’s the scale

설명

OpenAI 고객 사례 페이지(제품 표기: API)이고 전문을 읽었다. 글은 iFood 시니어 소프트웨어 엔지니어 Victor Coelho 한 명의 인터뷰로 구성된다. 사업 성과나 지출 규모는 공개하지 않았다.

과제가 어려워서가 아니라 1만5천 개 저장소라는 규모 때문에 막혔다

사실
  • iFood가 관리하는 코드 저장소는 1만5천 개가 넘는다. 사내 표준 검증, 취약한 의존성 수정, 분석 같은 작업이 저장소마다 주기적으로 필요하다.
  • 플랫폼이 생기기 전에는 팀마다 각자 해법을 만들었고, 모두 같은 장애물(실행 계층의 부재)에 부딪혔다.
  • 플랫폼의 목적은 각 팀이 업무 문제에만 집중하고 실행은 플랫폼에 위임하게 하는 것이다.

출처 1 · The challenge isn’t the task—it’s the scale

결정적 단계 사이에 에이전트 실행을 끼워 넣어 예측 가능성을 확보한다

사실
  • 사용자가 REST 호출로 프롬프트와 환경 요건을 보내면, 플랫폼이 격리 샌드박스 안의 전용 원격 러너에서 작업을 처리하고 결과는 나중에 회수하는 3단계 구조다. 진행 상황은 실시간으로 볼 수 있다.
  • 작업의 앞과 뒤는 결정적 단계로 고정했다. 앞에서는 저장소 복제, 에이전트가 쓸 스킬 가져오기, 작업 브랜치 설정을 하고, 뒤에서는 머지 리퀘스트를 게시하고 산출물을 공개한다. 그 사이에서 GPT‑5.6 Luna가 에이전트로 실행된다.
  • 샌드박스는 Ubuntu이며 Python, Java, Kotlin, C#, TypeScript, Rust, JavaScript, Go 툴체인을 갖췄다. 에이전트는 샌드박스 밖의 Nexus, GitLab, Docker, Snyk, Kubernetes, AWS에도 접근한다.
  • 설계는 OpenAI의 Batch API와 Agents API에서 직접 영감을 받았다. 인터페이스 설계, 리소스 구성, 비동기 실행 후 결과를 회수하는 방식까지 닮게 만든 사내 버전이다.

출처 1 · A coding agent in the cloud, accessible through an API; Modeled on the APIs that inspired it

해석

구조 자체를 새로움으로 읽을 근거는 글에 없다. 인터페이스와 비동기 회수 방식은 OpenAI의 Batch API·Agents API를 본떴다고 글이 스스로 밝힌다. 투자 관점에서 의미 있는 대목은 따로 있다. 대기업 고객이 OpenAI의 패키지형 코딩 에이전트 제품이 아니라 원시 API 위에서, OpenAI 자사 API의 형태를 본떠 사내 런타임을 직접 지었다는 점이다. 같은 페이지의 '더 읽기'에 Codex 사례가 함께 걸려 있다는 점과 대비된다. 다만 글에 다른 제품을 검토했다는 언급은 없으므로, 왜 직접 지었는지는 알 수 없다.

실행 1건 평균 4센트, 건당 비용이 아키텍처를 정하는 변수가 된다

사실
  • 누적 실행은 2만5천 건 이상, 소비 토큰은 270억 개 이상이며 실행 1건의 평균 추론 비용은 0.04달러다.
  • 모든 실행에 GPT‑5.6 Luna를 쓴다. 같은 체크포인트의 모델들 가운데 벤치마크상 지능·효율·실행 속도의 균형이 뛰어나서 골랐다고 한다. 하나의 요인이 아니라 세 요인을 함께 따졌다.
  • 본문은 수만 개 토큰을 소비하는 상황에서는 건당 4센트가 사소한 수치가 아니라 아키텍처 고려사항이 된다고 쓴다.
  • 앞으로 사내 여러 사용 사례로 확장할 계획이며, 확장을 지속할 수 있을지는 작업당 비용이 결정한다고 밝혔다.

출처 1 · Why GPT‑5.6 Luna; Results at a glance; Next steps

계산

공개된 세 수치를 결합하면 실행 1건당 약 108만 토큰, 누적 추론 지출 약 1,000달러, 토큰 100만 개당 약 0.037달러가 나온다. 실행 건수와 토큰 수가 모두 '이상'으로 표기된 하한값이므로 비율은 근사치다.

누적 실행
25,000건 이상
누적 토큰
270억 개 이상
실행 1건 평균 비용
US$0.04

식: 건당 토큰 = 270억 ÷ 25,000 ≈ 108만; 누적 지출 = 25,000 × 0.04 ≈ 1,000달러; 100만 토큰당 비용 = 0.04 ÷ 1.08 ≈ 0.037달러

해석

이 결합값에서 두 가지를 짚는다. 첫째, 본문의 '수만 개 토큰을 소비하는 상황'이라는 구절은 건당인지 누적인지 밝히지 않는다. 건당이라면 결합값(건당 약 100만 토큰)과 어긋나고, 누적 270억 토큰의 단위를 잘못 옮겼을 가능성도 있다. 둘째, 100만 토큰당 4센트 미만이라는 함축 단가는 대부분이 할인된 캐시 입력 토큰이거나, '평균 추론 비용'의 정의가 일부 비용을 뺐을 때에만 나올 수 있는 값으로 보인다. 원문만으로는 어느 쪽인지 가릴 수 없다(확신 낮음).

비용 정의가 불확실하므로 누적 지출 약 1천 달러도 하한 근사로만 읽는다. 그대로라면 OpenAI 매출 기여는 아직 미미한 수준이다(확신 중간). GPT‑5.6 Luna가 플래그십인지 경량 모델인지는 글에 없다. 확인되는 것은 효율을 지능·속도와 함께 따져 골랐다는 점뿐이다.

Structured Outputs로 에이전트가 일을 끝냈는지 기계가 판정한다

사실

세션이 끝나면 결과를 OpenAI의 Structured Outputs로 처리해, 미리 정한 계약 형식을 따르게 강제한다. 결과가 성공이든 실패든 세션마다 반드시 응답을 얻도록 해서, 규모가 커져도 목표 달성 여부를 자동으로 분류한다.

출처 1 · How to tell whether the agent completed the task

원문

Victor Coelho · iFood 시니어 소프트웨어 엔지니어

Structured Outputs로 결과를 처리하면 응답이 미리 정한 계약을 따르게 된다. 덕분에 불확실성이 줄고, 결과가 긍정이든 부정이든 에이전트 세션에서 항상 응답을 받을 수 있다.

출처 1 · How to tell whether the agent completed the task

해석

형식이 계약을 따른다고 해서 판정 내용이 정확하다는 보장은 없다. 에이전트가 자기 작업을 '성공'으로 보고했을 때 그 판정이 실제로 맞는지, 그리고 생성된 머지 리퀘스트가 얼마나 병합되는지를 보여 주는 수치는 글에 없다.

첫 사용자인 보안 플랫폼에서 수정 정확도와 해결 건수가 두 배 이상으로 늘었다

사실
  • 1만5천 개 저장소에서 취약한 의존성을 찾아 수정을 시도하는 사내 보안 제품이 이 플랫폼 위로 옮겨 왔다.
  • 이전 후 수정의 정확도와 해결한 취약점 수가 모두 두 배 이상이 됐다. 첫머리 요약은 해결 건수만, 인터뷰 발언은 정확도만 언급한다.
  • 보안팀은 에이전트 런타임을 직접 만들거나 오케스트레이션 전문가가 될 필요 없이 API를 호출하기만 하면 됐다.

출처 1 · The first major user: security; Results at a glance

해석

'두 배'의 기준선이 빠져 있다. 이전 방식이 규칙 기반 도구였는지 다른 모델이었는지, 정확도를 무엇으로 쟀는지(병합률인지, 테스트 통과율인지), 측정 기간이 얼마였는지가 없다. 따라서 이 수치는 개선의 방향을 보여 주는 정도로만 읽는다.

가치는 빨리 끝내는 데보다 감독하지 않아도 되는 비동기 실행에 있다

사실

작업을 위임하면 감독 없이 돌아가므로, 개발자는 회의 중에도 코드 수정이나 성능 분석 같은 반복 작업을 띄워 둘 수 있다. 글은 인력 대체가 아니라 판단이 필요한 문제에 쓸 시간을 돌려준다는 쪽으로 효과를 설명한다. 생산성 수치는 제시하지 않았다.

출처 1 · Asynchronous execution gives developers their time back

근거가 어디서 왔는가

설명
  • 모든 수치(저장소 수, 실행 건수, 토큰, 건당 비용, 두 배 개선)는 iFood의 자체 집계를 OpenAI가 옮긴 것이다. 독자가 독립적으로 검증할 수 있는 근거는 없다.
  • 발언자는 엔지니어 한 명이다. 경영진 시각이나 예산 규모, 다른 팀의 채택 현황은 나오지 않는다.
  • 모델 선택의 근거로 든 '벤치마크'의 이름과 비교 대상은 공개하지 않았다.

글이 지목한 수혜자

사실
  • OpenAI 제품으로는 GPT‑5.6 Luna, Structured Outputs, 그리고 설계의 본보기가 된 Batch API·Agents API가 등장한다.
  • 에이전트가 접근하는 외부 도구로는 Nexus, GitLab, Docker, Snyk, Kubernetes, AWS가 나열된다. 결과물은 머지 리퀘스트 형태로 나온다.
  • 피해자나 경쟁 제품은 언급하지 않는다.

출처 1 · A coding agent in the cloud, accessible through an API; Modeled on the APIs that inspired it

비판적으로 다시 읽기

해석
  • 말하는 자리: 글을 낸 곳은 API를 파는 OpenAI다. 'Lessons for leaders'와 'Tips'에 담긴 권고(사내 API로 노출하라, 비용·지능·속도를 함께 보고 모델을 고르라, 구조화 출력을 쓰라)는 모두 OpenAI API 사용을 늘리는 방향이다.
  • 수치의 내적 일관성: '수만 토큰을 소비하는 상황'이라는 구절은 건당인지 누적인지 밝히지 않는다. 그래서 건당 약 100만 토큰이라는 결합값과 어긋나는지조차 판단하기 어렵다. 100만 토큰당 4센트 미만이라는 함축 단가도 비용 정의를 의심하게 한다.
  • 빠진 반대 근거: 실패율, 사람의 검토 부담, 머지 리퀘스트 거절률, 잘못된 수정이 낳은 사고 여부가 없다. 저장소 1만5천 개를 '커버한다'는 말도 실제로 돌린 저장소 수와 같다는 뜻인지 불분명하다.
  • 규모에 대한 착시: 2만5천 건과 270억 토큰은 큰 숫자로 보이지만, 함축 지출은 약 1천 달러다. 대기업 하나의 '규모 있는 도입'이 아직 실험적 예산 수준일 수 있다.

작성자의 생각과 투자자 관점의 정리

해석
  • 확인된 것: 대기업 고객이 에이전트를 비동기 배치 작업처럼 돌리고, 지능·효율·속도를 함께 따져 고른 모델로 건당 비용을 설계 변수로 다루는 방식이 운영되고 있다(판매 자료 속 고객 발언 기준). 토큰 소비는 실행 건수에 비례해 커지는 구조다(확신 중간).
  • 새로 나온 것: 고객이 원시 API와 구조화 출력으로 사내 런타임을 직접 짓는 경로가 OpenAI 자체 판매 자료에서 모범 사례로 제시됐다. 매출이 패키지 제품 좌석보다 API 사용량에서 나오는 쪽으로 기울 가능성을 보여 주는 사례 하나다(확신 낮음, 표본이 하나다).
  • 답하지 않은 것: 총지출, 확장 계획의 규모와 시점, 정확도의 정의, 비용 정의(캐시 할인 반영 여부). 매출 추정에 쓸 수 있는 수치는 사실상 없다.
  • 실적·밸류에이션에 주는 뜻: 토큰 사용량이 커도 낮은 건당 단가 때문에 고객당 매출은 작을 수 있다. 사용량 성장을 매출 성장으로 바로 옮기는 전제는 경계해야 한다(확신 중간).
  • 다음에 확인할 것: 같은 유형의 고객 사례에서 공개되는 건당 비용과 누적 지출, 모델 가격 체계에서 캐시 입력 할인이 차지하는 비중, 사내 런타임과 패키지 에이전트 제품 가운데 어느 쪽이 기업 채택의 다수인지.
